# Status page forecast banner and backlog board

## Objective

Give `status.html` the same answer the index and the command now carry. When this is done, the page opens with a forecast banner and a backlog board showing batches, ready work, and what is waiting — above the existing charts, and generated from the metrics document rather than by parsing anything.

## Context

`status.html` is the surface a person opens in a browser, regenerated by `path close` and never hand-edited. It charts burn-up, volatility, decision latency, and drift, and says nothing about what to do next. Of the three no-terminal surfaces — the index, the page, and the command — it is the one that stays silent.

Relevant documentation:

- [F-55 — the status page must present the same queue](../requirements/03-functional.md#tasks)
- [F-34 — the page is generated from the metrics document](../requirements/03-functional.md#metrics)
- [F-56, F-57 — rate and forecast](../requirements/03-functional.md#metrics)

## Prerequisites

T-115 for rate and forecast, T-118 for the settled shape of what the queue says. Both recorded in `path.requires`.

## Scope

- A forecast banner above the charts: rate over the stated window, remaining points, projected finish date, and the derived caveat where it applies, reusing the existing provenance banner treatment.
- A backlog board: one section per non-complete batch plus an ungrouped section, ready tasks as first-class rows, waiting rows visually secondary and labelled with what they need, complete work collapsed to a count.
- Everything read from `metrics.build()`. No new parsing of any kind.
- The insufficient-data case renders as a plain statement in place of the projection, never as a blank or a zero.

### Out of Scope

- Any new chart.
- Computing rate, forecast, readiness, or rollups. All of it arrives in the metrics document.
- Changing when the page is regenerated. `path close` continues to own that.

## Notes

Three surfaces now answer the same question, and the risk is that they answer it differently. The defence is that all three read `metrics.build()` and none of them sorts or filters on its own. Any ordering rule that appears in this file rather than in the metrics document is a bug in the making.
