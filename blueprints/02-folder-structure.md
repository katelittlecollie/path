# Path — Folder Structure

## Standard Project Layout

Every project using Path follows this structure:

```
/[project-name]/
  AGENTS.md                           # AI navigation guide; CLAUDE.md is a pointer to it
  /.path/
    index.md                          # OKF directory listing (no frontmatter)
    /requirements/
      01-overview.md                  # What the project is and why it exists
      02-user-stories.md              # Who uses it and for what
      03-functional.md                # What the system must do (numbered F-XX)
      04-non-functional.md            # Quality attributes (numbered NF-XX)
      [05-...].md                     # Additional requirement topics as needed
    /blueprints/
      01-architecture.md              # System design and key decisions
      02-folder-structure.md          # File/directory layout (this file for Path itself)
      [03-...].md                     # Additional topics: data model, API, security, etc.
    /tasks/
      index.md
      TASK-TEMPLATE.md                # Template for new tasks
      T-001-[short-slug].md           # One file per task
      T-002-[short-slug].md
      ...
    /build-log/
      index.md
      [YYYY-MM-DD]-[topic].md         # One file per decision/event/session
    /strategy/                        # Only if a direction is being explored
      index.md
      [YYYY-MM-DD]-[topic].md         # One file per speculation/debate thread
    decisions-log.md                  # Only if a decision has actually been raised
    status.html                       # Regenerated by `path close`; never hand-edited
```

`.path/` is a dotfile, deliberately — the same convention as `.git`, `.github`, `.vscode`: it reads as tooling rather than as project content, and cannot collide with a project's own source tree wanting to use the plain name `path`.

## Naming Conventions

### Projects
Project folder names should be lowercase, hyphenated, and descriptive. Examples: `mail-client`, `invoice-tool`, `path`.

### Requirements and Blueprint Files
- Prefixed with a two-digit number to control reading order: `01-`, `02-`, etc.
- Named by topic in lowercase-hyphenated form.
- Topics are chosen per project — the overview/user-stories/functional/non-functional set is the minimum, not a fixed list.

### Tasks
- Named `T-[NNN]-[short-slug].md` where NNN is zero-padded to three digits.
- Slugs are lowercase-hyphenated and describe the task, not the outcome. Example: `T-003-implement-login-flow.md`.
- Numbers are allocated by the `path` CLI, sequential, and never reused once anything refers to them — see `blueprints/03-conventions.md`.

### Build Log Files
- Named `[YYYY-MM-DD]-[topic].md`.
- If multiple entries are written on the same day, append `-2`, `-3`, etc.
- Topic is lowercase-hyphenated and describes what the entry is about.

### Strategy Files
- Named `[YYYY-MM-DD]-[topic].md`, same as build-log.
- If multiple entries are written on the same day, append `-2`, `-3`, etc.
- Topic is lowercase-hyphenated and describes the direction being explored.

`strategy/` holds speculation, debate, and direction-setting — the thinking
that happens *before* a decision is settled or a file is changed. `build-log/`
is the opposite: a record of what was actually done, decided, or changed, in
the past tense. A strategy note may argue several ways and reach no conclusion;
that is expected. When a strategy thread resolves into a real choice, that
choice is recorded where settled things live — a `DECISION` build-log entry, an
entry in `decisions-log.md`, or an updated requirement or blueprint — not left
in `strategy/`. Neither folder is required; both appear only once there is
something to put in them.

## File Count Guidance

Requirements and blueprints should have as many files as needed for clarity, but no more. A five-line requirement does not need its own file — combine related small topics. A sprawling architecture file that covers six unrelated concerns should be split.

The test: can a reader find what they need without reading files that aren't relevant to them?

## Where Source Code Lives

Path documentation lives in `.path/`. Source code lives wherever is appropriate for the project's tech stack (e.g., a separate `src/` directory, a monorepo, a separate repository). `AGENTS.md` should reference the source code location if it is not co-located.

## Path's Own Structure

This repository is the one documented exception to the layout above: it is self-hosted, with `requirements/`, `blueprints/`, `tasks/`, `build-log/`, and `strategy/` sitting at the top level rather than nested under `.path/`. A `.path/.path/` directory would be its own kind of joke — see `blueprints/01-architecture.md`'s "Three Homes" section for why the product repository, the personal profile, and a consumer project are three genuinely different things and only the last one nests under `.path/`.
